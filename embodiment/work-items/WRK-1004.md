# WRK-1004 — Extend the CLI into the minimal Core host

Status: proposed; implementation not started. Prerequisite: WRK-1000. Follows code reconciliation and precedes WRK-1001. Requirements: REQ-1002, REQ-1003, REQ-1008. Decisions: DEC-1001, DEC-1002, DEC-1004.

## User-visible result

Bill launches the same project and can converse through a small local browser page. Closing the page leaves the host running. Reopening it retrieves the current conversation; restarting the host retains committed conversation records and the companion identifier. The existing CLI remains available.

## Starting evidence and scope

LOCAL-CLI-BASELINE.md reports working ModelPort, LM Studio adapter, JSON configuration and CLI. WRK-1000 supplies actual paths and code revision. Extend that project; reuse any additional core functionality discovered during reconciliation. Do not build another model loop or duplicate persistence if it already exists.

## Implementation

1. Factor or reuse a Core entry point around existing ModelPort. Keep one active primary inference; route CLI/browser input through the same conversation handling. Preserve explicit model configuration and actual-model telemetry.
2. Implement the minimum source ledger and conversation/attachment projections required by the parent contracts in the same application's SQLite store. Keep one durable writer, a stable configured companion ID, attributed committed inputs/outputs, and a visible record of failures or interruptions. This is conversation continuity, not a claim of completed semantic memory or personality development.
3. Serve the local browser page and expose conversation, current snapshot, and ordered event subscription. Wire the CLI through the shared Core implementation; do not allow simultaneous independent hosts to write the same database.
4. Add the thin capability registry/dispatch/receipt seam needed by BodyPort and the inspection view for requests/outcomes. No broad tool catalog is required. Bill-originated requests can exercise this seam; do not falsely claim model tool support from a successful text response. Inspect structured-action output support and document the route before enabling model-originated body actions. Do not infer intent by scanning ordinary dialogue for gesture keywords.
5. Keep ModelPort calls asynchronous so a slow response leaves the page and control path responsive. Preserve provider failures visibly. Implement only cancellation the underlying route can honestly support; local speech cancellation in WRK-1002 must work independently.

## Acceptance

- One browser exchange uses the existing LM Studio adapter/configuration and produces a committed conversation record.
- Reload/reopen restores current state; restart retains committed records and the same companion identifier.
- Existing CLI still works with the shared implementation; no second personality prompt or memory owner is introduced.
- Snapshot ordering and the capability receipt seam are available to WRK-1001. The avatar is not required for this host demonstration.

Run the existing typecheck and narrow relevant checks when code changes warrant them; demonstrate the new flow once. Avoid a broad hardening campaign or repeated live calls to benchmark the reported 32-second response. Record actual paths, commands, code revision and a brief result.

## Recovery, exclusions and handoff

Use the existing database backup/migration path or establish its minimal first version alongside the first database; failed startup preserves existing data. Preserve original CLI behavior and configuration. Full memory retrieval/consolidation, autonomy scheduling, custom avatar production and speech are outside this prerequisite. Reuse relevant parent continuity/Glass Box work without declaring those whole work packages complete unless their own acceptance is actually met.

Handoff to WRK-1001 with the host launcher, real interfaces and known model action-output support. No work is complete merely because this document exists. Implementation remains subject to Bill's future build instruction.
